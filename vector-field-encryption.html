Vector Field Encryption

Encrypts text and files by walking every byte through a 64 MB cube of random arrows and writing down how far it walked. Everything happens inside this page, and it reads the same key files as the Windows app.

Key

A key is 64 MB of random data read as a 256³ cube. It can be a seed key, 32 random bytes expanded into the cube on the fly, which fits in a line of text you can share; or a raw key, the 64 MB itself, which is what the Windows app uses (codebook.iotp and vec.iotp). Either kind can be saved as one .vfek file or exported as the classic pair. The key stays in this tab's memory unless you tick “remember”.

Index records

Choose a goal under “Characters per index” and encrypt to see the chains.

The older version in VFE/old/VectorFeildScan.cs tried to write a whole message as one index. Here each record is one index: a length, a start cell and an offset from which the arrows spell the next characters. Chains of n characters occur once per 256n−2 start-and-second-cell pairs, and a 64 MB key has 4.3 billion of them, so about six characters per index is the ceiling for ordinary text; runs of one repeated byte are the exception, since a cell can point at itself.

Download

Expect somewhere between 50 and 150 KB per second. For every byte, the cipher takes about five hundred dependent random steps through the 64 MB key, and each step is a cache miss. A 1 MB file takes around ten seconds; a 100 MB file, closer to half an hour. Encrypted files use the Windows app's names: photo.jpg becomes photo.jpg_enc, and decrypts back to photo_dec.jpg.

How it works

  1. The key is a 256 × 256 × 256 cube. Every cell holds one random byte (the codebook) and one random arrow to another cell (the vector field).
  2. To encrypt a byte, start where the last walk ended and follow arrows, each one XOR-ed with a running position vector, until you land on a cell whose codebook byte matches. Write down how many steps that took, from 1 to 255: that number is one hop of the ciphertext.
  3. If 255 steps go by without a match, write down a 0, let the position vector and offset shift, and keep walking from where you are.
  4. Every message opens with 10 to 255 random bytes, a random position vector and offset, and a random number of state shuffles, so the same text never encrypts the same way twice and ciphertext is roughly 1.6 times the size of the message plus a few hundred bytes of setup.
  5. Decryption replays the walk: follow exactly that many steps and read the byte you land on. It never checks whether the byte could have been reached sooner, so any cell on the path holding the byte is a valid hop and a 0 can be spent on purpose; the original program always takes the first hit, which is the freedom the multi-hop search uses.

This cipher is an independent developer's experiment and has not been reviewed by cryptographers. Enjoy it as a project; for anything that matters, use audited tools such as age, GPG or Signal.
